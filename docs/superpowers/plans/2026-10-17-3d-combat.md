# Interactive 3D Combat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native execution, or superpowers:subagent-driven-development if the user selects that method. Track steps with checkboxes.

**Goal:** Replace browser RPG battles with articulated 3D creatures, visible move-specific weapons, elemental choreography, and interactive attack/guard/capture commands; polish related scene events without breaking the combined campaign.

**Architecture:** The existing engine and battle queue remain authoritative. Pure command/recipe modules feed an event-driven three.js battle presenter; models, arenas and effects have separate ownership. Python mirrors gameplay and readable feedback through pygame, while the full 3D presentation belongs to the browser game.

**Tech Stack:** JavaScript, existing vendored three.js r128, Canvas/DOM HUD, Python/pygame, Node tests, existing Playwright/Chromium harness.

**Spec:** `docs/superpowers/specs/2026-10-17-3d-combat-design.md` (approved).

## Global Constraints

- Real 3D creatures and arenas in every supported browser RPG battle context; sprites with extra particles do not fulfill this requirement.
- All 26 species and every existing move require explicit coverage; preserve species silhouettes, colors and distinguishing features.
- Every action visibly uses its correct weapon/body part/emitter in preparation, execution, result and recovery. Cover both fighters.
- Preserve saves, offline play, the dedicated game-window launcher, campaign descent/checkpoints/return and Python data/gameplay parity.
- Use the installed r128 API; no ordinary-play network requirement and no imported commercial art.
- Keep DATA/ENGINE/STATE import-safe and deterministic. Separate cosmetic RNG; engine default behavior and random-call counts remain unchanged.
- ON/ASSIST/AUTO timing settings, independent reduced motion, bounded visual quality settings and explicit WebGL failure/basic-mode recovery.
- No Git repository exists: back up all affected sources before editing, work in place, and retain the execution ledger and verification evidence.

## Review Focus

- A weapon attachment missing on an unusual creature must fail coverage checks rather than produce an invisible attack.
- Focus loss during a held charge/catch must pause timing and require fresh input, without a free result or stuck state.
- Miss, immunity, capped status, double KO and evolution must preserve truthful visual/result ordering.
- Repeated battle/overworld/underground transitions must not retain render loops, GPU contexts, sound or input listeners.
- WebGL loss, blocked storage and old saves must preserve a playable campaign and clearly identify degraded presentation.

### Task 1: Command judgment and engine parameters

**Interfaces:** `createCommand(kind, mode, context)`, `stepCommand(command, dt, input)` and `judgeCommand(kind, elapsed, mode, context)` are pure. Kinds: strike, charge, guard, catch. Modes: ON, ASSIST, AUTO. Context: normal, hunt, ace. Result: `{tier, damageScale, critBonus, throwScale}` with unused scales equal to 1 and unused critBonus 0. Python provides equivalent snake_case functions/tables.

**Exact profiles:** strike duration 1.0s, target .65s, Good half-window .14s, Perfect .055s; charge duration 1.2s, target .85s, Good .16s, Perfect .065s; guard duration .9s, target/cue .58s, Guard .12s, Perfect .045s; catch duration 1.2s, target .95s, Nice .22s, Great .13s, Excellent .055s. Boundaries are inclusive. ASSIST doubles half-windows, capped to command duration. Hunt multiplies half-windows by .8, ace by .9, normal by 1. Context does not alter duration/target. A fresh press arms hold/release commands; stale held keys cannot resolve them.

**Modifiers:** Good attack 1.1; Perfect 1.2 plus .05 crit probability, capped at 1 total crit probability. Guard .8; Perfect guard .65. Catch Nice/Great/Excellent 1.15/1.5/1.85. Timeout/no input gives baseline attack/catch 1 and guard 1. AUTO resolves Good/Guard/Great at the target without input. Effects never alter the modifier after judgment.

### Task 2: Queue integration, settings and actual player input

**Interfaces:** add `cmd` and `action` queue steps. An action descriptor is `{id, actor:'mine'|'foe', moveId, target, result, duration, contactAt}`. Queue progression triggers the authoritative result exactly once at contact and completes only after recovery; a separate command step resolves timing first. Pure `sampleAction(action, elapsed)` reports phase/progress and never mutates HP. Model/presenter effects consume events, not gameplay RNG.
